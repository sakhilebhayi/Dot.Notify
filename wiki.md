# Dot.Notify

Purpose: this is Dot.Notify's own knowledge home — owned and maintained by the Dot.Notify team. It describes what this platform actually does, how it's built, and how it connects to the wider Dot Ecosystem. Dot.Brain never edits this file; it only reads what we choose to publish.

> **Related:** [Dot.Brain's ingested view of this platform](https://github.com/sakhilebhayi/Dot.Brain/blob/main/platforms/dot-notify.md)

## 1. What Dot.Notify Is

Dot.Notify sends, tracks, and optimises notifications on behalf of the rest of the ecosystem — email, SMS, push, webhook, Slack, and in-app. Teams configure delivery channels, build message templates (with AI-assisted drafting), map trigger events to routing rules, and get an audit trail of every notification from queue to send (queued, sending, retrying, sent, failed, suppressed). Notify records that a channel accepted a message; it does not receive opens, clicks, bounces or inbox-delivery confirmations, so it does not report them.

We are the shared last mile: almost nothing here originates as Dot.Notify's own idea — a platform tells us "this event happened," and we decide, per team-configured rule, who gets told, on what channel, with what copy. That position is also what makes our data unusually valuable: we are the only platform that sees attention economics across the *whole* ecosystem — what gets sent, failed or suppressed by an opt-out, regardless of which platform triggered it. (Opens and clicks are not captured today; that attention signal is still ahead of us.)

**Status:** shipping. This is a working Laravel application, not a blueprint — channels, templates, rules, delivery logs, batches, and schedules are all implemented and running behind team-scoped auth. Inbound webhooks are the one exception by design: `POST /webhooks/{token}` is a real, receiving endpoint (see §2 and §3), but it deliberately sits outside session/Sanctum auth — external systems call it, they don't log in — and authenticates instead via a per-webhook token plus an HMAC-SHA256 request signature.

## 2. Architecture

| Layer | Technology |
|---|---|
| Framework | Laravel 12 (PHP 8.4) |
| Frontend | Livewire 3, Alpine.js 3, Tailwind CSS |
| Database | PostgreSQL 16, shared across the ecosystem |
| Realtime | Laravel Reverb |
| Auth | Laravel Sanctum, ecosystem SSO handoff |
| AI | Anthropic Claude (`claude-sonnet-4-6`) for template drafting |
| Queue | Laravel queue (`QUEUE_CONNECTION`; `database` by default, `redis` in the production example). A worker must run: `php artisan queue:work` (see `deploy/queue-worker.*`). Horizon is not installed |
| Search | Laravel Scout + Meilisearch |

**Ecosystem SSO:** `App\Http\Controllers\Auth\EcosystemAuthController` (`GET /auth/ecosystem?token=`) logs a person in from an InfoDot handoff token. Because this app has its own database, it sends the token to InfoDot's signed redeem endpoint (`App\Services\InfoDot\IdentityClient`, `INFODOT_SERVICE_SECRET` = `ECOSYSTEM_SECRET_NOTIFY` in InfoDot), then matches or provisions the user and syncs their companies (`SyncTeamsFromInfoDot`). A company is a team with `teams.infodot_team_uuid` set (`php artisan infodot:link-team`); that uuid is the only shared name for a company, and it is what the ingest API below uses. The older shared-database path, a local Sanctum token with the `ecosystem:read` ability, still works and is spent on use. Multi-tenancy is Jetstream teams: every domain table (`notify_channels`, `notify_templates`, `notify_rules`, `notify_logs`, `notify_batches`, `notify_schedules`, `notify_webhooks`) is scoped by `team_id`.

**Service ingest API:** `POST /api/ingest/events` (`App\Http\Controllers\Api\IngestEventController`, `routes/api.php`) is how another Dot app asks Notify to tell someone something. Server to server, no session. The CALLER signs: `X-InfoDot-Timestamp` (unix seconds, 5 minute tolerance) and `X-InfoDot-Signature: sha256=<hmac_sha256("{timestamp}.{raw body}", platform secret)>`, the same scheme as InfoDot's other signed calls with the direction reversed (`App\Services\Notify\IngestSignature`). Each platform has its own secret, `NOTIFY_INGEST_SECRET_<KEY>` (`config('notify.ingest.secrets')`); blank means that platform cannot call, and unknown platform, blank secret, bad or stale signature all give the same `401 {"error":"invalid_request"}`. Payload: `{platform, company_uuid, event, recipient: {email} | {user_email}, data: {…}, idempotency_key (≤120), channel?, sensitive?: [data keys to mask], notification_type?}`. `company_uuid` maps to `teams.infodot_team_uuid` (unknown company: `404`). The company's own active `NotifyRule` for `event` (`trigger_event`, oldest first) picks the template and channel; the caller cannot supply a template, and may only name one of its own company's active channels (`channel`, by name or id; otherwise `422 unknown_channel`). With no active rule the event is recorded as `no_rule`, nothing is sent and no rule is created. Results: `202 {id, status}` (`routed`, `no_rule`, `ignored` for a rule rate ceiling, `failed` for an unusable rule), `200` with the original id for a replay of the same `(company, platform, idempotency_key)` (enforced by a unique index; sends nothing), `422` bad payload, `429` over `NOTIFY_INGEST_RATE_LIMIT` per platform+company per minute. Events are stored in `notify_inbound_events` (`notify_webhook_id` null); fields in `sensitive`, and any key that looks like a secret, are masked in the stored payload and in `body_preview`, with the real text kept encrypted in `notify_logs.body` only until the send finishes. **Event catalogue:** `config/notify_events.php` (`App\Services\Notify\NotifyEventCatalogue`) is the versioned list of the 16 events the Dot apps send, each with its platform, label, default channel (email), recipient kind (`user` or `approvers`), default template and the only `data` keys it may carry. For a catalogued event the ingestor keeps only those keys, turns control characters into spaces, cuts text at 500 characters, refuses a nested array under an allowed key (`422`), drops any `url`/`*_url` that is not an absolute https URL on the calling platform's registry host, records the dropped key names as `payload.dropped_data_keys`, takes `notification_type` from the catalogue, and accepts a catalogued event only from the platform that owns it (otherwise `no_rule`). Events the catalogue does not know are still accepted as before, unfiltered. A company switches events on from `/connected-apps` (owner/admin; `App\Livewire\Notify\ConnectedApps`) or `php artisan notify:enable-defaults {company_uuid} {platform?} {--events=}`, both through `App\Services\Notify\EventEnabler`: it creates, once, the company's own template (slug `catalogue.<event>`) and an active rule on its first active email channel, never overwrites an edited template, and disabling only deactivates rules. With no active email channel the rule is created flagged "no channel" and events are recorded as `failed` until one is added. The README section "Event catalogue and enabling events" is the contract for calling apps.

**Queued delivery:** a `NotifyLog` is delivered by `App\Jobs\DeliverNotifyLog` (queued, unique per log until a worker starts it, 5 tries) which runs one attempt through `App\Services\NotifyDispatcher`. The attempt first claims the row with a single `UPDATE … WHERE status IN (queued, retrying) AND due`, so a duplicate job or second worker cannot send twice. Then, in order: the recipient's `NotifyPreference` opt-out is checked (`suppressed`; `security` notices are never suppressed), then the channel driver sends. Permanent failures (4xx other than 408/425/429, invalid email, blocked URL, redirect) set `failed` at once; transient ones (5xx, 408/425/429, timeouts, connection and SMTP errors) set `retrying` with `next_retry_at` after 30s, 2m, 8m, 32m, and the 5th failure is final. `attempts`, `last_error`, `next_retry_at`, `last_attempt_at` and `sent_at` record each attempt. `notify:dispatch-queued` (every minute) is only a sweeper: it enqueues up to 100 due logs, oldest first, and never sends; a row stuck in `sending` for 15 minutes (a worker died mid-send) is marked `failed` with "outcome unknown" rather than re-sent, because it may already have gone out. This is at-most-once for crashes and at-least-once for retries of failures the destination reported.

**Outbound hardening and secrets:** webhook and Slack channels call team-supplied URLs through `App\Services\Notify\SafeHttp`: http/https only, no credentials in the URL, the host is resolved and every address must be public (loopback, RFC1918, link-local such as 169.254.169.254, CGNAT, `::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped IPv6 and numeric host spellings are refused), the connection is pinned to the checked address, 5 second timeout, redirects are never followed, and the body is HMAC-signed (`X-Dot-Timestamp`, `X-Dot-Signature`) when the channel config has a `secret`. Error text stored on a log has URLs reduced to scheme and host, since a Slack webhook URL is itself a secret. `notify_channels.config` and `notify_webhooks.signing_secret` are encrypted at rest (`encrypted:array` / `encrypted` casts; migration `2026_10_18_120200_encrypt_notify_secrets_at_rest` is idempotent). They depend on `APP_KEY`, so rotate it with a re-encrypt step.

**Authorization:** channels, rules, templates, webhooks and schedules have policies (`App\Policies\TeamResourcePolicy`): every team member can read, only the team owner or an `admin` can create, change or delete, so `editor` is read-only. The Livewire managers enforce them, and `NotifyRule` refuses a channel or template from another team at the model layer.

**AI template drafting:** `App\Services\AiNotifyService::generateTemplate($purpose, $channelType)` calls the Anthropic Messages API directly (raw cURL, no SDK) with a fixed prompt asking for `{subject, body, variables}` JSON using `{{ variable }}` interpolation syntax. If no API key is configured it falls back to a deterministic templated stub rather than failing — AI assistance degrades gracefully to a usable default, it never blocks the send path.

**Inbound webhooks:** `POST /webhooks/{token}` (`App\Http\Controllers\WebhookInboundController`, registered in `routes/web.php` outside the `auth:sanctum`/session group) is the real receiving endpoint for third-party events — closing the gap this wiki previously flagged as unbuilt. It is unauthenticated in the Jetstream sense on purpose: external systems (Stripe, GitHub, etc.) call it directly, so it authenticates via a two-part scheme instead:

1. `{token}` (`NotifyWebhook::endpoint_token`) identifies *which* webhook.
2. The `X-Dot-Signature` header must equal `hash_hmac('sha256', $rawRequestBody, $webhook->signing_secret)`, checked with `hash_equals()` — never `==` — against the header value.

Both branches of failure — an unknown token, and a known token with a missing or wrong signature — return the exact same generic `401 {"message": "Unauthorized."}`. The controller always derives *a* secret (a deterministic fallback hash of the token when no real webhook is found) and always runs `hash_hmac` + `hash_equals`, so an unknown-token request and a bad-signature request cost roughly the same and are never distinguishable from the response. Nothing is persisted for a rejected request, so there's no admin-visible trace an attacker could use to tell "wrong signature" apart from "no such webhook." The route carries `throttle:30,1` since it's a public, unauthenticated-by-design surface.

On a verified request, a `NotifyInboundEvent` row records the payload, `verified_at`, and a `status` (`received` → `routed` or `ignored`). If the webhook's `event_map` resolves the payload's event name to one of the team's `trigger_event`s and an active `NotifyRule` exists for it, the controller creates a `NotifyLog` (status `queued`) using that rule's `template_id`/`channel_id` — the same per-recipient audit record every other send path in this app produces — and links it back on the `NotifyInboundEvent`. It does not invent a parallel delivery mechanism, and it does not itself send: the queued log is picked up by the minute sweeper and delivered by the queued job (see "Queued delivery" above).

## 3. Domain Entities

Derived from `database/migrations/2026_06_29_200001_create_notify_tables.php`, `2026_08_01_150001_add_signing_secret_to_notify_webhooks_table.php`, `2026_08_01_150002_create_notify_inbound_events_table.php`, and `app/Models/`:

| Entity | Table | Key fields | Notes |
|---|---|---|---|
| **NotifyChannel** | `notify_channels` | `type` (email/sms/push/webhook/slack/in_app), `config` (encrypted array), `is_active`, `test_status` | Driver-specific credentials (SMTP, Slack webhook URL, webhook URL + optional signing `secret`) live in `config`, encrypted at rest |
| **NotifyTemplate** | `notify_templates` | `subject`, `body`, `variables` (JSON), `channel_type` | `{{ variable }}` interpolation; can be AI-drafted via `AiNotifyService` |
| **NotifyRule** | `notify_rules` | `trigger_event`, `conditions` (JSON), `template_id`, `channel_id` | Maps a trigger event (`user.signup`, `payment.failed`, `custom.*`) to a template + channel |
| **NotifyLog** | `notify_logs` | `recipient`, `status`, `attempts`, `last_error`, `next_retry_at`, `last_attempt_at`, `sent_at`, `notification_type`, `event`, `body` (encrypted, transient) | Per-recipient audit record; `status` walks queued → sending → sent, or retrying → …, or failed / suppressed. `delivered_at`/`opened_at` columns and the delivered/opened/clicked/bounced statuses exist only on old rows; nothing writes them |
| **NotifyPreference** | `notify_preferences` | `user_id`, `notification_type`, `channel_type`, `event`, `enabled` | Per-user opt-in/out, unique per (user, type, channel, event). `event = ''` is the category-wide row; a catalogued event name is a per-event opt-out (`NotifyPreference::setForEvent`). `security` is never suppressed |
| **NotifyBatch** | `notify_batches` | `status`, `total_recipients`, `sent_count`, `failed_count` | Bulk sends with progress tracking |
| **NotifySchedule** | `notify_schedules` | `cron_expression`, `timezone`, `next_run_at` | Recurring sends tied to a rule |
| **NotifyWebhook** | `notify_webhooks` | `endpoint_token` (unique, auto-generated), `signing_secret` (auto-generated, hidden from serialization), `source`, `event_map` | Inbound webhook endpoints that translate a third-party event into one of our `trigger_event`s; `signing_secret` backs the HMAC scheme above |
| **NotifyInboundEvent** | `notify_inbound_events` | `payload` (JSON, secrets masked), `source_event`, `trigger_event`, `verified_at`, `status` (`received`/`routed`/`ignored`/`no_rule`/`failed`), `notify_log_id`, `notify_webhook_id` (null for ingest), `platform`, `idempotency_key` | One row per signature-verified inbound webhook request or service ingest event; only ever created after verification passes; unique per (team, platform, idempotency_key) |

Consent lives on `NotifyPreference`, scoped per user × notification type × channel — this is the enforcement point for anything opt-out-sensitive.

## 4. Events Emitted

Delivery status transitions on `NotifyLog` are the primary signal we produce for the rest of the ecosystem:

| Event (status) | Meaning | Where it's set |
|---|---|---|
| `queued` → `sending` → `sent` | The channel accepted the notification (SMTP accepted / HTTP 2xx / bell row written) | `App\Services\NotifyDispatcher` |
| `retrying` | Transient failure; tried again at `next_retry_at` | `last_error` populated |
| `failed` | Permanent failure or 5 attempts used | `failure_reason` populated |
| `suppressed` | Recipient opted out (`NotifyPreference`) | `failure_reason` names the preference |

Nothing reports delivery, opens, clicks or bounces back to Notify, so those statuses are not produced and not shown. Dashboard aggregates (`routes/web.php`) read the real ones: active channel count, sent today, failures today, retrying now, suppressed (30 days), template count — all team-scoped. Livewire components react to a `notify.sent` browser event (see `NotificationCenter::refresh()`) to live-refresh the log view via Reverb.

**Inbound side:** as of this pass, `NotifyInboundEvent` rows are a second, upstream signal — every verified third-party webhook request, whether or not it matched an active `NotifyRule` (`status`: `routed` vs `ignored`). An `ignored` event with a `source_event` that never maps in any `event_map` is a concrete, queryable signal of a webhook integration that's misconfigured or a third party sending events this team never wired up — useful input for a future `observation` Knowledge Pack (see §5), not yet built.

## 5. Connecting to Dot.Brain

Dot.Notify participates in the ecosystem as a registered platform (`dot-notify`) that publishes Knowledge Packs about delivery performance and attention economics — never about message content or recipient identity beyond aggregate cohorts.

| Payload type | Cadence | Contains |
|---|---|---|
| `observation` | weekly | per-class precision (acted / sent) and fatigue aggregates |
| `insight` | per finding | attention-economics patterns that only a cross-platform last-mile can see |
| `outcome` | per verified recommendation | before/after metrics for accepted class-throttling or channel-selection changes |
| `incident` | per incident | delivery failures, consent breaches, runaway send volume |

We subscribe to Dot.Brain recommendations on class-throttling (demoting low-precision notification classes to digest), channel selection, and send-window optimisation — never frequency-pressure tactics. Full manifest, entity/event mapping, the domain-agent assignment (Documentation Agent), the Dot.Pulse cross-org consent seam, and a worked publish→PR round-trip are maintained on the Brain side at [`platforms/dot-notify.md`](https://github.com/sakhilebhayi/Dot.Brain/blob/main/platforms/dot-notify.md) — that document is Dot.Brain's ingested view and is authoritative for integration mechanics; this wiki is authoritative for what Dot.Notify actually *is* and how it's built.

**Governance note:** Dot.Brain's ingested view records a structural rule we enforce at our end — no notification class may trigger on recipient absence (no "we miss you" / inactivity nudges). Trigger conditions must reference domain events (`trigger_event` on `NotifyRule`), never recipient-behaviour gaps. That constraint isn't yet encoded as a validation rule in `NotifyRule` — see Roadmap.

## 6. Roadmap

- [x] Build the inbound webhook HTTP endpoint — `POST /webhooks/{token}`, `App\Http\Controllers\WebhookInboundController`, token + HMAC-SHA256 signature verification, routes into `NotifyRule`/`NotifyLog` (see §2, §3). Previously `NotifyWebhook` only issued tokens with nothing receiving on them.
- [x] Dispatch queued `NotifyLog` rows to an actual channel driver — `DeliverNotifyLog` job + `NotifyDispatcher` (retries, row claim, opt-outs); needs a running queue worker. Webhook-inbound logs are picked up by the minute sweeper
- [x] Service-authenticated ingest API for Dot apps (`POST /api/ingest/events`), idempotent and per-platform signed
- [x] Event catalogue for the Dot apps (`config/notify_events.php`), per-company enable/disable (Connected apps page, `notify:enable-defaults`), data sanitising on ingest, per-event opt-outs
- [ ] A recipient-facing preferences screen and a signed unsubscribe link in email footers (the opt-out is enforced, but nothing yet lets a recipient set it)
- [ ] Delivery confirmation, open/click and bounce tracking — nothing produces these yet (and no tracking pixel exists); would need provider callbacks or a tracking endpoint
- [ ] HTML email (email is plain text only), an editor for `NotifyPreference`, and role-aware hiding of write buttons in the UI (the server already refuses)
- [ ] Implement `NotifySchedule` model — the migration table exists but nothing reads/writes it yet
- [ ] Implement Knowledge Pack publishing (`observation`, `insight`, `outcome`, `incident`) — not yet wired up; this wiki and the Brain-side doc describe the target shape, not shipped behavior
- [ ] Enforce "no absence-triggers" as a validation rule on `NotifyRule` creation, not just a documented convention
- [ ] Per-class rate ceilings on `NotifyRule`/`NotifyBatch` to cap runaway send volume (the 2026-02 incident class of failure)
- [ ] Cost-aware channel-selection recommendations for SMS-heavy classes
- [ ] Expand `AiNotifyService` beyond template drafting (e.g., send-window suggestions) once Brain-side recommendations are consumable
